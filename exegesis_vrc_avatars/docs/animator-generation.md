# Animator generation

ncho's FX controller is partly hand-built and partly **generated by two editor tools**, both
written on [Animator As Code](https://github.com/hai-vr/av3-animator-as-code) (AAC). This
documents what they own, the invariants they encode, and the parts of the job AAC does not do.

## The two generators

| Tool | Menu | Owns | Assembly |
|---|---|---|---|
| `RcsAnimatorSetup.cs` | `Tools > Exegesis > Build RCS Animator Layers` | every layer named `rcs_*` | `Exegesis.RcsThruster.Editor` |
| `NchoSlotSetup.cs` | `Tools > Exegesis > Build ncho Slot Layers` | every layer named `slot_*` | `Exegesis.Ncho.Editor` |

**Run slots first, then RCS.** The slot tool declares the `back_slot` / `thigh_slot` ints that
the RCS group layers condition on. The menu is ordered by priority to match. Everything else in
`ncho_fx.controller` — panels, face, tail, `props_neutral`, `wing_deploy` — is hand-built and
must not be touched by either tool, with one deliberate exception noted below.

Two assemblies on purpose: `NchoSlotSetup` needs the VRChat SDK for `VRCAvatarParameterDriver`,
and the shader tooling must not take an SDK dependency — a version bump would otherwise break
the shader inspector and the RCS tool along with it.

Supporting code lives in two more assemblies: `Exegesis.Shared.Editor` (no AAC, no SDK —
`ControllerSnapshot`, `AnimatorParameters`, `AnimatorAssets`) and `Exegesis.Aac.Editor`
(`ExegesisAac`, `ExegesisDefaultsProvider`).

### Why generated at all

The controller carries dozens of layers. Hand-editing that YAML mangles GUIDs, and hand-editing
it through the Animator window is slow and unrepeatable. Both tools are **idempotent**: they
delete and rebuild everything matching their prefix, so re-running is always safe and is the
expected way to apply a change. `GeneratorIdempotenceTests` pins that the committed controller
is exactly what a fresh run produces.

Teardown matches on **prefix, not a name list**. An earlier rename left an orphaned layer behind
because its old name was no longer in the list the teardown consulted.

### The one exception to "owns only its prefix"

`NchoSlotSetup` also, deliberately:

- **deletes** the four hand-built layers it replaced (`thruster_backpack`, `arm_pack`,
  `thigh_hard-cases`, `thigh_thrusters`) — one-way, and their clips are retained and reused;
- **edits** the hand-built `wing_deploy` layer to strip `rcs` from its conditions.

Both are logged. The `wing_deploy` edit is code rather than a hand edit for one reason: **a
transition whose conditions are all removed is always true.** Stripping `rcs` from the
standalone `If rcs` entry transition would leave an unconditional path into the deployed state —
strictly worse than the bug being fixed. The tool deletes a transition left with no conditions
and only edits in place when other conditions survive.

This stays hand-written. AAC has no vocabulary for "modify what is already there"; everything it
touches, it rebuilds.

## The invariants

Everything below is load-bearing and non-obvious. This is the list any reimplementation has to
satisfy; each row names the test that pins it.

### Write Defaults OFF, everywhere

Every state in this controller — generated and hand-built — has `writeDefaultValues = false`.
That is what lets the layers stack: a layer sitting in a state that writes nothing lets lower
layers win.

Two consequences that have each cost real time:

- **A state playing an empty clip writes nothing**, so the property keeps whatever it last held.
  A gate clip that should force a value to 0 but has *no curve* silently holds the material's
  saved value instead. → `GeneratedClipTests`
- **"Bare" needs no clip.** A slot layer in `idle` writes nothing, so the accessory tiles fall
  through to `props_neutral`'s hidden values. This is why slots have no state for 0.

`ExegesisDefaultsProvider` passes `writeDefaults: false` to AAC, which applies it to every state
it creates.

### Every generated clip writes something

`VerifyGeneratedClips()` reloads the controller **from disk** after the build and errors on any
clip the `rcs_*` layers reference that carries no curves. Reloading is the point: it checks what
was actually serialized, which is the only version the animator will ever play. This caught a
real failure once — one clip out of 38 written with `m_FloatCurves: []` while every other clip in
the same build came out correct. → `GeneratedClipTests`

The audit is scoped by **reachability from the `rcs_*` layers**, not "every clip in the file".
The controller carries two orphaned clips from an old duplicate-the-controller operation, one of
which legitimately has no curves; auditing everything would report a permanent, unfixable
failure that has nothing to do with the generators.

### Direct blend trees sum their children

`rcs_smooth`, the publish layers and `rcs_imu` all depend on a Direct blend tree with
**Normalize Blend Values OFF**, which makes it *sum* rather than average. Children writing
different properties coexist in one tree; children writing the same property form a lerp (the
smoother) or a signed pair (the IMU).

No public scripting property exposes this, and **AAC never touches it** — a grep of all three
hai-vr packages finds no reference to `m_NormalizedBlendValues` at all. Unity defaults it off,
but the design is far too dependent on it to leave to a default, so
`AnimatorAssets.SetNormalizedBlendValues` sets it through `SerializedObject` on every Direct tree.
→ `Snapshot_DetectsInjectedDifference`

### Publish is eight 1D layers, not one Direct tree

One Direct tree holding all eight children is tidier and was tried. It measured **dead** on the
live material: master and the group gates were correct while `_RCS_Vel` stayed at 0.000 through
any amount of motion, because the weight parameter `RCS_One` did not arrive at its default of 1.
A 1D tree reads its blend parameter directly, so there is no weight left to arrive as zero. The
extra layers cost nothing — the VRCFury optimiser merges them straight back.

`rcs_imu` still leans on `RCS_One` for its neutral base child. It has not misbehaved, but if the
IMU ever reads as stuck at zero, start there.

### Clips can drive Animator parameters

Not just component properties. That is what lets `rcs_smooth` feed a parameter back into itself
to produce the exponential lag, with no arithmetic anywhere in the animator. In AAC this is
`AnimatesAnimator`.

### Slot exclusivity is structural

One int per mount point, one state per member, entered on `Equals <value>` and left on
`NotEqual <value>`. A state machine can only be in one state, so two accessories on one mount
are unrepresentable rather than merely prevented. → `SlotParameterTests`

Int conditions **must** use `Equals`/`NotEqual`. An `If`/`IfNot` against an Int parameter never
matches, and nothing logs it. This is why parameter declaration is **not** left to AAC — see
below. → `SlotParameterTests`

### Accessories fade, and swap sequentially

- **0.25 s transition duration**, `hasFixedDuration` true. The fade is **not in the clips** —
  they are two-key constants. It comes entirely from the transition duration, blending the
  dissolve alpha against `props_neutral`'s value on the layer below. A rebuild with a default
  duration of 0 removes the fade silently. → `SlotTransitions_KeepTheFade`
- **No member-to-member transitions.** Swaps route through `idle`, so the old accessory is
  fully gone before the new one appears. Direct transitions would be half the duration but
  crossfade, dissolving two pieces of solid hardware into each other. This is the intended look,
  inherited from ChoccyWicker. → `SlotMembers_SwapViaIdleNotDirectly`

The second is a test asserting the *absence* of an optimisation, because the shortcut is
tempting and nothing in the code says the extra hop is deliberate. It was implemented as a
crossfade once and had to be reverted.

Transition **order** is creation order, in AAC as in the raw API. The two loops in
`BuildSlotLayer` stay separate for that reason: all of `idle`'s entry transitions first, then one
exit transition per member.

### Presets are one-shot

Each `slot_loadout` state hosts a `VRCAvatarParameterDriver` that Sets several slot ints **and
resets `loadout` to 0**. Without the self-reset the state re-enters continuously, re-fires the
driver every frame, and pins the slot ints so per-slot toggles can never win — the bug the
ChoccyWicker `Outfits` layer has. Preset transitions are duration 0: they carry no visuals.

## What AAC does, and the four things it does not

AAC owns layers, states, transitions, conditions, clips, blend trees and parameter drivers.
Everything below is handled by this project because AAC does not do it, and each has a comment
in the source saying what breaks without it.

### 1. Parameter declaration — `AnimatorParameters`

AAC's `CreateParamIfNotExists` matches **by name only**. A parameter already declared with the
wrong type is silently left alone, and an `Equals` condition against something the controller
believes is a Bool never matches and never logs — this project's recurring failure shape.
`AnimatorParameters.Ensure`/`EnsureInt`/`EnsureFloat` correct the type and warn.

Note the deliberate asymmetry: `EnsureFloat` **overwrites** the default (blend-tree weights the
tool owns outright), while `Ensure` and `EnsureInt` **preserve** it (VRChat expression parameters
carrying saved user values — no build tool should reset what someone is wearing).

Driver targets and clip bindings use `aac.NoAnimator()`, which returns parameter handles without
registering anything. A preset names parameters this tool does not own (`hard-case_mounts`,
`arm_hard-cases`); `layer.FloatParameter` would silently declare any that were missing, with a
guessed type.

### 2. Layer teardown — `ExegesisAac.RemoveLayersByPrefix`

Run **before** AAC sees the controller, so AAC always takes its append-a-new-layer path. Its
other path, clearing a layer that already exists, empties the state machine by assigning empty
arrays over `states` and `anyStateTransitions` — which *detaches* those sub-assets without
destroying them. They then accumulate in the committed file on every rebuild.

### 3. Sub-asset cleanup — `AnimatorAssets.SweepUnreachableSubAssets`

AAC's own `ClearPreviousAssets()` only ever removes `AnimationClip`, `BlendTree` and
`AvatarMask` — never an `AnimatorState`, transition or behaviour — and it matches on the
`zAutogenerated/{AssetKey}__` name prefix, which stops working the moment an asset is renamed to
something readable.

The sweep works on **reachability** instead: anything in the controller file that nothing in
`controller.layers` points at is destroyed. That is strictly stronger, it does not care what
anything is called, and it means renaming generated assets and cleaning up after them stop
fighting each other. One owner for cleanup, not two.

**This is the one failure `ControllerSnapshot` cannot see** — the snapshot walks the reachable
graph, so an orphan is invisible to it and the file could double in size with every test still
green. `RebuildingTwice_DoesNotAccumulateSubAssets` is what holds that line.

### 4. Stable asset names — `ExegesisAac.Clip` / `DirectTree` / `Tree1D`

AAC names generated sub-assets `zAutogenerated/{AssetKey}__{name}_{Random.Range(0, int.MaxValue)}`,
with the integer drawn fresh on every call, and `NewBlendTree()` has no named overload at all so
its middle segment is a `Guid`. Left alone, the committed controller's diff churns on every
rebuild even when nothing changed — and reviewing that diff is the entire reason a generated
asset is kept in git.

These helpers rename past the decoration immediately. Clip names are also a contract
`GeneratedClipTests` asserts on.

## Where the generated clips live

**Inside `ncho_fx.controller`, as sub-assets.** They used to be 38 `.anim` files in
`ncho_anim/rcs_generated/`; AAC owns clip creation now and its assets go in the container it is
given. The folder is gone.

Hand-authored clips are unaffected and stay where they are: `_Empty.anim` and the
`[props]_*_on.anim` accessory clips are source assets, referenced by GUID, not generated.

## `ExegesisDefaultsProvider`

Two of AAC's four virtual members are overridden.

**`ConvertLayerNameWithSuffix`** returns `{system}_{suffix}` — single underscore, where AAC's
default is double. `rcs_group_packs`, not `rcs__group_packs`. The tests, the docs and the
prefix-teardown convention all hardcode the current names.

**`ConfigureTransition`** reproduces what Unity's `AddTransition` leaves behind, which differs
from AAC's defaults in two fields: `exitTime` is **0.9**, not 0, and `canTransitionToSelf` is
**true**, not false. Both values were measured off the committed controller through
`ControllerSnapshot`, not assumed — and both would have been guessed wrong.

Neither can change behaviour here: `exitTime` is unreachable while `hasExitTime` is false, and
`canTransitionToSelf` only matters for Any-State transitions, which no generated layer has. They
are reproduced anyway. An equivalence diff that is genuinely empty is worth much more than one
that is empty except for two differences carrying a footnote about why they are fine — next
time, the footnote is what someone reaches for.

The same reasoning covers `ExegesisAac.FinishTree1D`, which restores the `directBlendParameter`
of `"Blend"` that Unity puts on 1D blend tree children and AAC leaves empty. Dead data on a 1D
tree; reproduced so the diff stays honest.

## Scene-less by construction

`AacConfiguration.AnimatorRoot` and `DefaultValueRoot` are both null. `AnimatorRoot` is only ever
dereferenced by AAC's `Transform`, `GameObject` and `Component` clip overloads and by
`ResolveAvatarMask`; `DefaultValueRoot` is documented as unused in AAC's own source. Using only
the string-path overloads (`Animates(path, type, property)` and `AnimatesAnimator`) keeps the
generators runnable with no scene loaded, which is what lets them work in the headless clone.

`GeneratedClips_BindOnlyByStringPath` pins it from the other side: every generated curve must
bind an Animator parameter at the empty path, or a material property at `Body` or `Props`.

## What not to change

Clip names (`rcs_group_packs_covered`, `rcs_group_thighs_worn`, …), the `_GroupEnable` component
mapping, and the slot int values. Clip names and components are asserted by `GeneratedClipTests`;
the slot values are a saved-parameter contract with every user who has worn the avatar, and the
group indices are baked into **vertex green on the meshes** — see
[rcs-thrusters.md](rcs-thrusters.md) and [accessories.md](accessories.md).

## Note for a fresh clone

`Packages/*` is gitignored, so AAC's source is not committed. The headless clone is populated by
robocopy from the working tree rather than by git, so it gets AAC — but a fresh `git clone` needs
VPM resolution before the first compile, or the generator assemblies fail to build.
