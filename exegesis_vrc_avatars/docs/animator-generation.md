# Animator generation

ncho's FX controller is partly hand-built and partly **generated by two editor tools**. This
documents what they own, the invariants they encode, and what a migration to
[Animator As Code](https://github.com/hai-vr/av3-animator-as-code) would have to preserve.

## The two generators

| Tool | Menu | Owns | Assembly |
|---|---|---|---|
| `RcsAnimatorSetup.cs` | `Tools > Exegesis > Build RCS Animator Layers` | every layer named `rcs_*` | `Exegesis.RcsThruster.Editor` |
| `NchoSlotSetup.cs` | `Tools > Exegesis > Build ncho Slot Layers` | every layer named `slot_*` | `Exegesis.Ncho.Editor` |

**Run slots first, then RCS.** The slot tool declares the `back_slot` / `thigh_slot` ints that
the RCS group layers condition on. The menu is ordered by priority to match. Everything else in
`ncho_fx.controller` — panels, face, tail, `props_neutral`, `wing_deploy` — is hand-built and
must not be touched by either tool, with one deliberate exception noted below.

Two assemblies on purpose: `NchoSlotSetup` needs the VRChat SDK for `VRCAvatarParameterDriver`,
and the shader tooling must not take an SDK dependency — a version bump would otherwise break
the shader inspector and the RCS tool along with it.

### Why generated at all

The controller carries dozens of layers. Hand-editing that YAML mangles GUIDs, and hand-editing
it through the Animator window is slow and unrepeatable. Both tools are **idempotent**: they
delete and rebuild everything matching their prefix, so re-running is always safe and is the
expected way to apply a change.

Teardown matches on **prefix, not a name list**. An earlier rename left an orphaned layer behind
because its old name was no longer in the list `RemoveExistingLayers` consulted.

### The one exception to "owns only its prefix"

`NchoSlotSetup` also, deliberately:

- **deletes** the four hand-built layers it replaced (`thruster_backpack`, `arm_pack`,
  `thigh_hard-cases`, `thigh_thrusters`) — one-way, and their clips are retained and reused;
- **edits** the hand-built `wing_deploy` layer to strip `rcs` from its conditions.

Both are logged. The `wing_deploy` edit is code rather than a hand edit for one reason: **a
transition whose conditions are all removed is always true.** Stripping `rcs` from the
standalone `If rcs` entry transition would leave an unconditional path into the deployed state —
strictly worse than the bug being fixed. The tool deletes a transition left with no conditions
and only edits in place when other conditions survive.

## The invariants

Everything below is load-bearing and non-obvious. This is the list a reimplementation has to
satisfy; each row names the test that pins it.

### Write Defaults OFF, everywhere

Every state in this controller — generated and hand-built — has `writeDefaultValues = false`.
That is what lets the layers stack: a layer sitting in a state that writes nothing lets lower
layers win.

Two consequences that have each cost real time:

- **A state playing an empty clip writes nothing**, so the property keeps whatever it last held.
  A gate clip that should force a value to 0 but has *no curve* silently holds the material's
  saved value instead. → `GeneratedClipTests`
- **"Bare" needs no clip.** A slot layer in `idle` writes nothing, so the accessory tiles fall
  through to `props_neutral`'s hidden values. This is why slots have no state for 0.

### Clips are authored before the asset is created

`MaterialClip`/`ParamClip` build curves on the in-memory clip and call `PersistClip`
**afterwards**. The reverse order — `CreateAsset`, then `SetEditorCurve`, then rely on
`SetDirty`/`SaveAssets` — lost the curves on exactly one clip out of 38 in a build where every
other clip was correct. `VerifyGeneratedClips()` reloads every clip **from disk** after the
build and errors on any with no curves. → `GeneratedClipTests`

### Direct blend trees sum their children

`rcs_smooth`, the publish layers and `rcs_imu` all depend on a Direct blend tree with
**Normalize Blend Values OFF**, which makes it *sum* rather than average. Children writing
different properties coexist in one tree; children writing the same property form a lerp (the
smoother) or a signed pair (the IMU).

No public scripting property exposes this, so `NewTree` sets `m_NormalizedBlendValues` through
`SerializedObject`. It defaults to off, but the design is too dependent on it to leave to a
default.

### Clips can drive Animator parameters

Not just component properties. That is what lets `rcs_smooth` feed a parameter back into itself
to produce the exponential lag, with no arithmetic anywhere in the animator.

### Slot exclusivity is structural

One int per mount point, one state per member, entered on `Equals <value>` and left on
`NotEqual <value>`. A state machine can only be in one state, so two accessories on one mount
are unrepresentable rather than merely prevented. → `SlotParameterTests`

Int conditions **must** use `Equals`/`NotEqual`. An `If`/`IfNot` against an Int parameter never
matches, and nothing logs it — so `EnsureParameter` in both tools *corrects a type mismatch*
rather than skipping a parameter that already exists. → `SlotParameterTests`

### Accessories fade, and swap sequentially

- **0.25s transition duration**, `hasFixedDuration` true. The fade is **not in the clips** —
  they are two-key constants. It comes entirely from the transition duration, blending the
  dissolve alpha against `props_neutral`'s value on the layer below. A rebuild with a default
  duration of 0 removes the fade silently. → `SlotTransitions_KeepTheFade`
- **No member-to-member transitions.** Swaps route through `idle`, so the old accessory is
  fully gone before the new one appears. Direct transitions would be half the duration but
  crossfade, dissolving two pieces of solid hardware into each other. This is the intended look,
  inherited from ChoccyWicker. → `SlotMembers_SwapViaIdleNotDirectly`

The second is a test asserting the *absence* of an optimisation, because the shortcut is
tempting and nothing in the code says the extra hop is deliberate. It was implemented as a
crossfade once and had to be reverted.

### Presets are one-shot

Each `slot_loadout` state hosts a `VRCAvatarParameterDriver` that Sets several slot ints **and
resets `loadout` to 0**. Without the self-reset the state re-enters continuously, re-fires the
driver every frame, and pins the slot ints so per-slot toggles can never win — the bug the
ChoccyWicker `Outfits` layer has. Preset transitions are duration 0: they carry no visuals.

## Migrating to Animator As Code

AAC **v1.2.0 is already installed** (`dev.hai-vr.animator-as-code.v1`, plus the `.vrchat` and
`.modular-avatar` sub-packages), pulled in transitively. Everything below was checked against
that source, not from memory.

### The fork that matters: destructive vs non-destructive

AAC's usual v1 flow is **non-destructive** — layers are generated at build time through NDMF /
Modular Avatar / VRCFury and never exist in a committed asset. Our model is **destructive**: the
tools write into `ncho_fx.controller`, and the result is committed and diffable.

That is not a stylistic preference here. **Every test inspects the committed controller** —
`SlotParameterTests` and `GeneratedClipTests` load `ncho_fx.controller` and assert on its layers,
transitions, conditions and clips. Going non-destructive means none of them can run as written;
they would have to build an avatar in-memory first.

`dev.hai-vr.animator-as-code.v1.vrchat-destructive-workflow` (1.1.2, **not installed**, available
in ALCOM) is the package aimed at this model — enable it before starting and verify what it
offers. Note core v1 already exposes `CreateMainArbitraryControllerLayer(controller)` and
`CreateSupportingArbitraryControllerLayer(controller, suffix)`, which operate on an arbitrary
controller, so a destructive migration may be largely possible without it.

**Recommendation: keep the destructive model.** The value of this setup is that the generated
result is committed, reviewable in a diff, and testable without a scene.

### Verified API mapping

| What we do now | AAC 1.2.0 | Notes |
|---|---|---|
| `state.writeDefaultValues = false` | `WithWriteDefaultsSetTo(false)`, or leave it — `AacDefaultsProvider(bool writeDefaults = false)` defaults to **false** | Matches this project |
| `AddCondition(Equals, v, param)` | `.When(layer.IntParameter(p).IsEqualTo(v))` | `IsNotEqualTo(int)` also present |
| `t.duration = 0.25f; t.hasFixedDuration = true` | `.WithTransitionDurationSeconds(0.25f)` | **AAC's default transition is duration 0** — see below |
| Curves on `material._Prop` at path `"Body"` | `clip.Animating(c => c.Animates("Body", typeof(SkinnedMeshRenderer), "material._Prop"))` | The **string-path** overload exists, so no scene object is needed |
| Clip driving an animator parameter | `c.AnimatesAnimator(param)` | The smoothing feedback loop survives |
| `VRCAvatarParameterDriver` by hand | `.Drives(param, value)`, `.DrivingLocally()` | In the `.vrchat` sub-package |
| Direct blend tree | `aac.NewBlendTree().Direct()` | **Normalization is not exposed** — see below |
| Prefix teardown (`rcs_*`) | `SystemName` + `ClearPreviousAssets()` / `AssetKey` | Naming changes — see below |

### Four things that will bite

1. **AAC's default transition duration is 0.** `AacDefaultsProvider.ConfigureTransition` sets
   `duration = 0`, `hasExitTime = false`, `hasFixedDuration = true`. So the 0.25s accessory fade
   is exactly the kind of thing a migration drops silently — the same regression that already
   happened once. `SlotTransitions_KeepTheFade` is the safety net; keep it running.

2. **Direct blend tree normalization is not exposed.** A grep of the whole package finds no
   `NormalizedBlendValues` anywhere. Unity's default is off, which is what the RCS design needs,
   but it would no longer be asserted. `AacFlBlendTree` exposes its underlying `.BlendTree`, so
   the existing `SerializedObject` poke can be reapplied — do that rather than trusting the
   default, because if it ever flips, the smoother averages instead of summing and the whole
   acceleration chain quietly changes meaning.

3. **Layer names change.** `AacDefaultsProvider.ConvertLayerNameWithSuffix` returns
   `$"{systemName}__{suffix}"` — double underscore. `rcs_group_packs` would become something
   like `RCS__group_packs`. Tests, docs and the prefix-teardown convention all hardcode the
   current names. **Subclass `AacDefaultsProvider` and override `ConvertLayerName` /
   `ConvertLayerNameWithSuffix` to preserve them**, and the existing suite keeps working
   unchanged — this is the single cheapest thing to get right early.

4. **`AacConfiguration.AnimatorRoot` is a `Transform`.** It is used to resolve relative paths for
   the `Transform`/`Component` overloads and for avatar masks. Our clips use string paths only,
   so it may be safe to leave null — *verify this*, because it decides whether the generators can
   still run without a scene, which is what lets them work in the headless clone.

### Order of work, if you do it

1. Enable the destructive-workflow package; confirm the entry points it offers.
2. Migrate `NchoSlotSetup` first. It is the smaller tool, it has the strongest test coverage, and
   it uses only mainstream AAC features — no blend trees at all.
3. Get `SlotParameterTests` green before touching anything else. It checks conditions, condition
   *modes*, thresholds, transition durations, transition ordering and Write Defaults, so it
   validates most of the AAC mapping in one run.
4. Migrate `RcsAnimatorSetup` last. It is the one with Direct blend trees, parameter-driving
   clips and the `SerializedObject` poke — the parts AAC covers least completely.
5. Keep `VerifyGeneratedClips()` or an equivalent. AAC creates clips its own way, so the specific
   ordering bug it guards may not apply, but "a generated clip that writes nothing" is a failure
   this project has already paid for once.

### What not to change while migrating

Clip names (`rcs_group_packs_covered`, `rcs_group_thighs_worn`, …), the `_GroupEnable` component
mapping, and the slot int values. Clip names and components are asserted by `GeneratedClipTests`;
the slot values are a saved-parameter contract with every user who has worn the avatar, and the
group indices are baked into **vertex green on the meshes** — see
[rcs-thrusters.md](rcs-thrusters.md) and [accessories.md](accessories.md).
